## 1. Por que e para onde

Hoje o NutroLab grava em `/srv/clinica/nutrolab-data/nutrolab.sqlite` (≈ 220 KB), via `node:sqlite`.
O alvo é um banco próprio, `nutrolab`, no Postgres 17.6 que já roda na stack (`/srv/clinica`, serviço `db`),
ao lado de `postgres` (clínica) e `ln_evolution`. Ganhos: backup único com `pg_dump` cifrado, concorrência
real, consultas cruzadas futuras com o LN Medicina Integrada e fim do arquivo SQLite dentro do volume.

Arquivos (PDFs, imagens, termos, logo, formulários) **continuam no disco** em `nutrolab-data/`; só o banco muda.

## 3. Mapeamento de tipos

| SQLite (hoje) | Postgres | Observação |
|---|---|---|
| `INTEGER PRIMARY KEY` | `bigint generated by default as identity` | ids preservados na cópia; sequência reposicionada depois (`setval`). |
| `INTEGER` (contadores, flags 0/1) | `integer` / `boolean` | `ai_used`, `requires_alert`, `checked`, `excluded` viram `boolean` (`= 1`). |
| `REAL` (faixas das regras) | `numeric(14,4)` | sem erro de ponto flutuante nas faixas; o motor continua convertendo para `number`. |
| `TEXT` datas `AAAA-MM-DD` | `date` | `birth_date`, `collection_date`, `reviewed_at`, `consent_at`. |
| `TEXT` `datetime('now')` (UTC, sem fuso) | `timestamptz` | interpretar como UTC na cópia (`… || 'Z'`); defaults viram `now()`. |
| `TEXT` ISO com `Z` (`expires_at`) | `timestamptz` | direto. |
| `TEXT` listas com `|` (`contexts`, `aliases`, `exams`…) | `text` (mantido) | trocar por `text[]` é refatoração separada; aqui só migra. |
| `TEXT` JSON (`score_json`, `details`, `items`) | `jsonb` | validar `json_valid` antes; `items` default `'[]'::jsonb`. |
| `CHECK (x IN (...))` | `CHECK` igual | mesmos valores. |
| FKs declaradas (`case_id → cases`) | `REFERENCES … ON DELETE RESTRICT` | exclusão continua lógica (`deleted_at`) nas tabelas que já usam. |

## 5. Camada de acesso (impacto no código)

Hoje todo acesso é síncrono: `getDb().prepare(sql).get/all/run` de `node:sqlite`, espalhado por rotas e scripts.

1. Criar `src/store/` com uma interface assíncrona (`one`, `many`, `exec`, `tx`) e duas implementações:
   `SqliteStore` (atual) e `PgStore` (driver `pg`, pool de 5 conexões; dependência nova, aprovar).
2. Migrar as chamadas para `await store.…`. É o maior trabalho: as rotas já são `async`, mas helpers
   como `evaluateCase`, `loadCase` e os geradores de relatório são síncronos e precisarão de `await`.
3. Diferenças de SQL a tratar: `datetime('now')` → `now()`; `IFNULL` → `coalesce`; `?` → `$1…`;
   `lastInsertRowid` → `returning id`; `PRAGMA` some; `INSERT … ON CONFLICT` igual.
4. Seleção por env: `DATABASE_URL` presente → Postgres; ausente → SQLite. Testes rodam nos dois
   (Postgres de teste via `pg` contra um banco efêmero, ou só SQLite no CI e Postgres no ensaio).
5. Estimativa: 2 a 3 dias de trabalho + ensaio. Pode ser feita em PRs pequenos (store primeiro, depois rota a rota).

## 6. Script de cópia (`scripts/migrate-to-postgres.ts`, a escrever)

1. Abrir o SQLite **somente leitura** a partir de uma **cópia** (`backup()` do `node:sqlite`), nunca do arquivo vivo.
2. `begin` no Postgres; aplicar `0001_init.sql` num banco vazio `nutrolab`.
3. Para cada tabela, na ordem das FKs (`users → patients → cases → case_files/results → rules/guidances →
   analyses → conduct_items → formulas/formula_files/conduct_templates → password_resets/settings/ai_usage/audit_log`):
   ler tudo, converter tipos (seção 3), inserir com o **mesmo id** (`overriding system value`).
4. `select setval(pg_get_serial_sequence('<t>','id'), coalesce(max(id),1)) from <t>` em cada tabela.
5. Validar (seção 7); se qualquer verificação falhar: `rollback` e sair com erro. Só então `commit`.

## 7. Validação

- **Contagens** por tabela: SQLite == Postgres (tabela da seção 2 regravada no dia).
- **Somas de controle**: `sum(id)`, `count(distinct exam_canonical)` em `rules`, `sum(score)` em `analyses`,
  `count(*) filter (where finalized_at is not null)`.
- **Amostras byte a byte**: `final_patient`/`final_technical` de cada análise final (hash sha256 igual).
- **Datas**: nenhuma `collection_date`/`birth_date` nula onde não era; nenhum timestamp deslocado (comparar 5 linhas).
- **Funcional** num container de ensaio apontado para o banco novo: login, abrir paciente, abrir caso,
  relatório (score igual ao gravado), PDF, API de integração (`/health`, `/cases/:id`, `/analyses/:id`).
- `npm test` rodando contra o `PgStore`.

## 8. Corte (janela do Dr. Leônidas)

1. Backup manual do SQLite (`dist/scripts/backup.js`) + `pg_dump` da stack; conferir que abrem.
2. Parar o `nutrolab` (`docker compose stop nutrolab`): sem escrita durante a cópia.

4. Pôr `DATABASE_URL=postgres://nutrolab_app:…@db:5432/nutrolab` no `.env` e subir o serviço.
5. Fumaça funcional (seção 7). O SQLite fica intocado e renomeado `nutrolab.sqlite.pre-pg` por 30 dias.

Usuário do banco: `nutrolab_app`, dono só do banco `nutrolab`, sem acesso aos demais (`GRANT` explícito).

## 9. Rollback

- Antes de ligar o Postgres: nada a desfazer, o SQLite continua em uso.
- Depois do corte, sem escritas novas importantes: remover `DATABASE_URL`, subir de novo → volta ao SQLite.
- Depois do corte, com escritas novas: exportar do Postgres as linhas com `id > max_id_do_corte` e
  `updated_at > hora_do_corte` e reaplicar no SQLite (script inverso, só para esse caso). Por isso a janela
  de observação recomendada é curta (24 h) antes de apagar o `.pre-pg`.
